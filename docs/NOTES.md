## 2. Architecture (target)
| Party | Role | Holds money? |
|---|---|---|
| Payer app (PSP) | User-facing; creates the idempotency key | No |
| NPCI switch | Routes, resolves VPA, tracks transaction state, generates RRN | **No** |
| Remitter bank | Debits the payer | Yes |
| Beneficiary bank | Credits the payee | Yes |

Happy path: payer app -> switch -> remitter debit -> switch -> beneficiary credit -> switch declares SUCCESS -> payer app.

Planned services: `bank-service` (two instances, separate DBs), `switch-service`, `psp-service`, later fraud and notification services, Kafka, API gateway.

## 3. Failure handling (the spec)
- **Technical decline:** system could not process it (timeout, node down, high CPU). Outcome may be unknown. Retry only with the **same transaction ID**.
- **Business decline:** system processed it and said no (unknown account/VPA, insufficient funds, wrong PIN, limits). Retrying will not help.

| Failure point | Money state | Action |
|---|---|---|
| Before debit (remitter down) | Nothing moved | FAILED, safe to retry |
| After debit, credit failed | Payer debited, payee not credited | Reverse the debit (new ledger entry, idempotent, retried until done) |
| Timeout, outcome unknown | Unknown | Do not guess: mark PENDING, status check, retry only with same ID, reconcile later |

Rules we worked out:
- Silence has two meanings (never arrived vs. processed but reply lost), so never guess.
- A status check is safe to repeat; a debit is safe to repeat only if idempotent.
- A pending deadline (about 5 min) triggers a **verification**, not a verdict. Reverse only when the debit is confirmed and the credit is not.
- The deadline timer is a server-side background job, not the app.
- A reversal must itself be idempotent.
- Idempotency key = the user's intent to make one payment: created on tapping Pay, saved on the phone **before** sending, reused on every retry, new only for a genuinely new payment. The PSP (closest to the user) creates it.
- After an app crash the app cannot know how far the request got, so it asks the server for the status by key (needs a lookup-by-key endpoint).
- Idempotency stops one payment applying twice; it does not stop a user making a second, separate payment (UX messaging covers that).

## 4. Terms
- **VPA:** Virtual Payment Address (`name@handle`), an **alias** for a bank account. Can change; one account can have several. Hence the bank keys accounts on `account_number`, not VPA.
- **RRN:** 12-digit Retrieval Reference Number, the shared reference for status checks, reconciliation and disputes. Generated by the switch. **Not** the idempotency key (that is `txn_id`).

## 5. Transaction states
| State | Meaning | Final? |
|---|---|---|
| INITIATED | Request received | No |
| DEBIT_PENDING | Debit sent, waiting | No |
| DEBITED | Payer's money left | No |
| CREDIT_PENDING | Credit sent, waiting | No |
| PENDING | Outcome unknown, needs status check | No |
| REVERSAL_PENDING | Debited, credit failed, refund in progress | No |
| SUCCESS | Both sides done | Yes |
| FAILED | Failed, no money impact | Yes |
| REVERSED | Money returned to payer | Yes |

## 7. bank-service: database design (db/schema.sql)
- `accounts`: `account_number` TEXT PK (stable, text keeps leading zeros), `ifsc_code` CHAR(11), `account_holder_name`, `balance` NUMERIC(14,2) with `CHECK (balance >= 0)`, `created_at`.
- `vpa_aliases`: `vpa` PK -> `account_number` FK (alias table; simplification, real UPI keeps this with the PSP/issuing bank).
- `ledger_entries`: one immutable row per money movement: `txn_id`, `rrn` (12 digits), `account_number` FK, `entry_type` in (DEBIT, CREDIT, REVERSAL), `amount > 0`, `balance_after >= 0`, `created_at`.
  - `UNIQUE (txn_id, entry_type)` = **idempotency enforced by the database** (one payment can have a DEBIT and later a REVERSAL, so the key is the pair).
  - Indexes on `rrn` and `(account_number, created_at)`.
  - Trigger `forbid_ledger_changes` makes it **append-only**: corrections are new rows, never edits (audit trail).
- Why NUMERIC: `0.1::float8 + 0.2::float8 = 0.30000000000000004`, `numeric` gives `0.3`. Never use float for money.
- Why checks live in the database: it is the last line of defense against bugs, races, and other writers.
- `db/tests.sql` proves each constraint fires; `db/seed.sql` loads accounts 1001 (10000) and 1002 (2500) with VPAs; `scripts/reset-db.ps1` rebuilds everything (dev only).

## 8. bank-service: application
- `config.py`: `pydantic-settings` reads `DATABASE_URL` from `.env` (no secrets in code). Start uvicorn from `services\bank-service` so `.env` is found.
- `db.py`: `psycopg_pool.ConnectionPool(open=False)`, opened/closed in the FastAPI `lifespan`.
- `/health` (liveness, no DB) and `/health/db` (readiness, `SELECT 1`, 2 s timeout, **503** if down). Kubernetes uses liveness to restart and readiness to stop traffic.
- `POST /debit` flow, all inside one DB transaction:
  1. Lock the account row (`SELECT ... FOR UPDATE`)
  2. Already applied for this `txn_id`? Return the original result (`idempotent_replay: true`); if same ID but different data, 409
  3. `balance < amount`? 422 `INSUFFICIENT_FUNDS`
  4. Update balance and insert the DEBIT ledger row together
  - Lock **before** the idempotency check, so two simultaneous same-`txn_id` requests serialize and the second finds the first's row. `UniqueViolation` handler is a safety net.
  - Status codes encode the spec: 404/422/409 are business declines (do not retry), 503 is a technical decline (retry with the same `txn_id`).
- Race to remember: two ₹800 debits on ₹1000 without a lock both read 1000, both pass, ₹1600 paid out (lost update). The row lock makes them sequential.

## 9. Lessons and troubleshooting log
| Problem | Cause | Fix |
|---|---|---|
| `docker` cannot connect to engine | Docker Desktop not running / WSL missing | `wsl --install`, restart, start Docker Desktop, `docker run hello-world` |
| Pulled `postgres:19rc1` | Release candidate | Use stable `postgres:18`; pin the major version |
| `git push` rejected (fetch first) | Remote had an earlier commit | Inspect, then `git push --force-with-lease` (only after checking what is overwritten) |
| Branch missing on GitHub | Push cancelled with Ctrl+C | Rerun `git push -u origin <branch>` and wait; check for a hidden sign-in window |
| `INSERT ... is not recognized` | SQL typed into PowerShell | SQL goes inside `psql` or in a `.sql` file piped via `Get-Content`; never in the PowerShell prompt |
| Pasted dialog text ran as commands | VS Code paste warning dialog | Click the dialog's Paste button; do not copy the dialog text |
| `cannot import name 'fastAPI'` | Case typo | The class is `FastAPI` |
| `failed to resolve host '123@localhost'` | `@` in the password broke the URL | Percent-encode the password (`@` = `%40`) or use key=value DSN; prefer simple dev passwords |
| Pylance `import could not be resolved` | VS Code using the wrong interpreter | Select `.venv\Scripts\python.exe` by path; cosmetic only |
| `requirements.txt` unreadable | PowerShell `>` writes UTF-16 | `pip freeze \| Out-File requirements.txt -Encoding ascii` |
| `Get-Content ... seed.sql` not found | File was never created | Create it in the editor first |
| Wrong variable in test (`$body` vs `$b`) | Copy slip | Double-check what each request sends |

Habits: check `git status` before every commit (`.env` and `.venv` must not appear); prove constraints by testing the failure cases; read the last two lines of a traceback first.
